# Racebench Full Run 2026-10-28 — the whole pipeline, all 31 simple cases

First end-to-end run of the complete tool (build → stage 1 → stage 2 → stage 3 → context → LLM
triage) on every simple [[Racebench]] case, after the fixes of [[Triage Study 2026-10-26]]. Track B
branch at `f93b5bd`; model `claude-cli:sonnet` (Claude Code on a subscription); prompt row
`+racebench` (the production row plus the benchmark-semantics add-on); LLM result cache cleared
first, so every answer is a fresh call; one sample. Run store:
`project-src/runs/bench-racebench-2026-10-28/` (`report.md`, `report.json`, `timings.tsv`);
scored by `project-src/scripts/bench-triage-report.py`.

## Scoring rule

The [[NASAC 2019 Prototype Competition]] rule for the simple cases: **+2 per bug point detected,
−3 per planted false-positive marker (trap) reported**. Denominators are the measured ground truth
(`2.1_remarks` + errata): **48 bug points, 38 traps**, maximum 96 — not the competition's 50/33.
A detection the suite annotates as neither bug nor trap is **not** a false positive (direction from
the human, 2026-10-28). Because the tool never drops a candidate without a proof, "reported" is
scored three ways.

| reported = | bug points | traps reported | score |
| --- | --- | --- | --- |
| LLM bucket `likely_real` | **46 / 48** | 5 / 38 | **77** |
| not called infeasible by the LLM | 46 / 48 | 6 / 38 | 74 |
| static stages only (everything reaching the LLM) | 48 / 48 | 16 / 38 | 48 |

- **The 5 traps reported are exactly the 5 disputed traps** — 001 #1, 019 #2–#4, 020 #1 — that the
  suite's own README semantics make reachable (`project-src/docs/masking-semantics.md`,
  [[Contradictions]] #7, [[Triage Study 2026-10-26]]). Against the 33 undisputed traps the LLM
  view reports none: score 92 of 96 if the disputed five are set aside.
- Trap disposition: 3 never generated by stage 1, 5 dropped by stage 2 (masking), 14 refuted by
  the solver (`unsat`), 10 called infeasible by the LLM, 1 `uncertain` (009 #1), 5 `likely_real`.
- Unannotated candidates: 102 reach the LLM; 38 land in `likely_real`, 64 in `likely_infeasible`.

## The two lost bug points — and what they say about the add-on

Both are in 017, both called infeasible by the add-on's **adjacency rule**: "the same flow
accesses the location again on every path between A1 and A2, so the benchmark counts the finer
triples" — the loop condition `global_var < MAX_LENGTH` re-reads the variable between the
annotated A1 and A2. But 017's own annotations mark those non-adjacent triples as bug points. The
rule was flagged as uncertain when drafted ("rests mainly on one case", 022); 017 contradicts it.
Its net effect on the score is +2 (it also rejects 022 traps #1 and #3, +6, and loses these two,
−4), bought with **recall** — the one trade the project does not make (`CLAUDE.md`: a model's
judgement may not drop a bug). This is the first and only `infeasible` verdict on a bug point in
any run since the record fixes. **The adjacency rule should come out of the add-on.**

## Funnel, ranking, time

- Candidates: stage 1 **316** → stage 2 **202** → reaching the LLM **166** (same as Track A's
  funnel; recall gate 48/48 through stage 3).
- Mean Inspection Ratio per case: **0.84** in the records' own order → **0.56** after triage.
- **Wall clock: 956 s (≈16 min)** with four cases in parallel; the per-case times sum to 3,534 s
  (mean 114 s, slowest 373 s for 017 with 18 candidates). **256 LLM calls**, about 13.6 s each
  under 4-way concurrency. Static stages total 29 s over all 31 cases (build 4.6 s, stage 1 3.5 s,
  stage 2 1.7 s, solver 18.3 s, context 1.3 s); the LLM is 99% of the time. No backend failure,
  no untriaged candidate. No case approaches the competition's 180 s limit for its static part.

Per-case table, every bug point and trap with its verdict: `report.md` in the run store.

## Reading

- On this benchmark the pipeline now behaves as designed: the static stages keep every bug point
  and remove 22 of 38 traps with proofs; the LLM then rejects 10 of the 11 undisputed traps that
  survive, while every remaining "false positive" is a label the suite's own semantics contradict.
- The score is one sample on one model; the run-to-run spread is not measured yet.
- The `+racebench` row is an evaluation row, not the production prompt, and its adjacency rule is
  now known to be wrong for the suite as well as unsafe for real code.

## Second run — adjacency rule removed (2026-10-28)

Same setup (cache cleared, `claude-cli:sonnet`, one sample), with the adjacency rule removed from
`racebench_semantics.md`. Run store: `project-src/runs/bench-racebench-2026-10-28b/`.

| reported = | bug points | traps reported | score |
| --- | --- | --- | --- |
| LLM bucket `likely_real` | **48 / 48** | 8 / 38 | **72** |
| not called infeasible | 48 / 48 | 9 / 38 | 69 |
| static stages only | 48 / 48 | 16 / 38 | 48 |

936 s wall clock (4 in parallel), 308 LLM calls, mean Inspection Ratio 0.86 → **0.72** — worse
than run 1's 0.56, because without the adjacency rule 84 unannotated candidates (38 in run 1) stay
in `likely_real`.

**The scoring had a matching artifact, now fixed.** The match rule compares lines, not access
kinds; when two candidates share the annotated lines (017's loop header writes and reads
`global_var` on line 29; `x++` reads and writes on line 30) the first by rank was taken — which in
run 1 credited two bug points to the *sibling* triples the adjacency rule had rejected. Matching now
prefers the kind-agreeing sibling (`evaluation.match_subject`; kinds still are not required). Run 1
re-scores identically (77): the two lost bug points are then 017 #1 and #3, also rejected by
adjacency.

## Verdict on every disputed item (human-requested review)

Each item read against the source and the suite's README ("an interrupt may preempt the main
program or a lower-level interrupt whenever it is enabled, at an indeterminate moment, position and
number of times"). Two kinds of disagreement, kept apart: **the label is wrong** under the suite's
own semantics, or **the model is wrong**.

| item | label | my reading | who is wrong |
| --- | --- | --- | --- |
| 001 trap #1 `W43 R63 W44` | trap | Reachable: `isr_1` may fire between `init()` (line 26, unmasks all) and `disable_isr(2)` (28), or a second activation starts with irq 2 already unmasked by the first (line 46). `isr_2` then lands between 43 and 44 and reads the intermediate 0 where the previous activation left 1. Same as Track A's W5 correction. | **label** |
| 019 trap #2 `R45 W71 R51` (errata lines) | trap | Valid in the `2.1` copy, where the read sits inside `disable_isr(1)…enable_isr(1)`: an ISR firing between 45 and 47 clears `condition3` and kills A2's guard. In the analysed `2.1_remarks` copy `enable_isr(1)` moved inside the `if`, before the read, so the ISR can fire after the guard passed. The label was not updated with the code. | **label (stale)** |
| 019 trap #3 `R51 W71 R59` | trap | Reachable in **both** copies: for A1 (needs `condition3 == 1`) and A2 (needs `condition3 == 0`) both to run, `isr_1` must run between them — and it writes `var1` while doing so. The two reads disagree. The label follows "each read in its own critical section", which the gap between `enable_isr` and the next `disable_isr` defeats. | **label** |
| 019 trap #4 `R48 W69 R56` (`condition3`) | trap | Reachable in both copies by the same gap; the two reads of `condition3` disagree — it is the very mechanism of the case's bug point. | **label** |
| 020 trap #1 `R37 W44 R40` | trap | Reachable with two `isr_1` activations: the first enables irq 2 and lets `isr_2` change `para` (so both guards can pass), the second writes `var` at 44 before the read at 40. The label assumes one activation. Track A recorded the same ([[Contradictions]] #7). | **label** |
| 022 traps #1 `W32 W66 R39`, #3 `R55 W66 R63` | "可能误报" (*possible* FP) | Reachable, but the local flow writes the variable again between A1 and A2 on every path, and the ISR writes the same value (0) that is already there: no observable effect. The annotator hedged ("possible"), and the same suite labels non-adjacent triples as bugs in 017. A convention, not an error on either side. | **neither** |
| 007 trap #1 `W32 W50 R34` | trap | Correct: the ISR increments the index before writing, so B writes `array[gv+1]`; A2 re-reads the index, so A1 and A2 touch different elements — not one location. Run 1 called it infeasible with exactly this argument; run 2 swapped B for the write at line 47 (`array[2]`), another triple. | **model** (unstable) |
| 009 trap #1 `W37 R47 W38` | trap | Correct: `isr_1` retargets `m` to its own local at line 46 just before reading `*m` at 47, and the task cannot preempt the ISR, so B never touches main's object. Both runs answered `uncertain`. | **model** (hedged, no recall cost) |
| 017 bugs #1, #3 (run 1) | bug | Feasible: the loop header reads the variable each iteration and the ISR writes it. Rejected in run 1 only by the adjacency rule; all four 017 bug points are `likely_real` in run 2. | **prompt rule** (removed) |

**Score with the suite's labels corrected.** Of run 2's 8 reported traps, 5 are label errors and 2
are 022's hedged "possible" false positives; 1 (007) is a model error. Treating the 5 label errors
as reachable: **87 / 96** (93 if 022's two "possible" ones are also set aside). Run 1, same
treatment: 92 / 96, but bought with two bug points. The remaining model errors are one false
positive (007, unstable across samples) and one hedge (009).

**Reading.** With the adjacency rule out, recall is complete (48/48) and every trap the model
accepts but one is either reachable under the suite's own README or explicitly hedged by its
annotator. The cost is ranking: the Inspection Ratio rises to 0.72 because the model now calls
most unannotated candidates real — many of which are genuine unannotated interleavings (the suite
does not claim its annotations are exhaustive). The variance between runs (007 flipped) is now the
largest unmeasured quantity.
